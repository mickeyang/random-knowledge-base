---

## 什么是缓存命中 / 缓存未命中？

你可以把 AI 想象成一个**需要看资料的员工**：

- **你发给 AI 的内容（输入）** = 你递给员工的参考资料
- **AI 回复你的内容（输出）** = 员工看完资料后写出的报告

### 缓存命中（Cache Hit）
你递过去的参考资料，**他刚才刚好看过**，还摊在桌子上没收拾。他直接说："哦这个我刚看过，不用重新读了，直接写报告吧。"
👉 **好处**：省时间（响应快）、省钱（很多平台对命中的 Token 打折扣，比如只收 1/10 的价格）。

### 缓存未命中（Cache Miss）
你递过去的参考资料，**他从来没看过**，或者之前看过但已经收进柜子里找不到了。他只能从头开始一页一页读。
👉 **后果**：慢一点、贵一点（全部按原价算 Token 费用）。

---

## 是不是只跟输入有关，跟输出完全没关系？

**你的理解完全正确 ✅**

缓存这回事，**100% 只针对你发给 AI 的内容（输入）**。

原因很简单：
- **输入**是你提前写好的东西（系统提示词、文档、对话历史），这些内容是可以重复利用的，所以值得存起来下次直接用。
- **输出**是 AI 根据你输入的内容**当场"现编"**出来的。哪怕你两次问一模一样的问题，从机制上讲，AI 也是实时生成的（除非设了 temperature=0 且模型完全确定性，但 API 层面不会把"生成的回答"当缓存来用）。

所以：
| | 跟缓存有关系吗？ |
|---|---|
| **输入 Token** | ✅ 有！命中就便宜/快，未命中就贵/慢 |
| **输出 Token** | ❌ 完全没关系，每次都是实时生成的 |

---

## 实际用起来要注意啥？

如果你在调 API，想多蹭点"缓存命中"省钱，核心技巧就一个：**尽量让你的输入前缀保持一致**。比如系统提示词放最前面别动，变来变去的内容放最后面。这样 AI 服务器就能认出"前面这段我存过"，前面那一大坨就命中缓存了。

# yuanbao response

给你整理一份**实操性很强的缓存命中优化清单**，核心目标就一个：**让 AI 服务器觉得"这段内容我刚看过"，从而按折扣价收费。**

---

## 🧠 一句话心法

> **缓存是按"前缀"匹配的。不变的内容放最前面，变来变去的内容放最后面。**

就像翻书——你每次翻到同一页，前面几章都一样，AI 就只需要读最后一章。

---

## ✅ 方法清单（从最有用到次有用排列）

### 1. 系统提示词放最前面，而且千万别随便改

这是**最大头的省钱机会**。系统提示词通常很长（几百上千 Token），而且每次请求都在。

| 做法 | 效果 |
|---|---|
| 系统提示词固定不动 | ✅ 每次都命中缓存 |
| 每次加个时间戳/随机 ID 在系统提示词里 | ❌ 前缀变了，缓存全废 |
| 调整系统提示词里的措辞 | ❌ 内容变了，缓存失效 |

**💡 实操建议**：系统提示词写好后就锁死。如果要加动态信息（比如当前日期），用变量注入到**用户消息**里，别动系统提示词。

---

### 2. 多轮对话：完整传历史，别只传最新的

很多人以为"我只发最新一句话给 AI 就行"，然后自己在本地拼上下文。错！

| 做法 | 效果 |
|---|---|
| 每次请求都带上完整对话历史（按原顺序） | ✅ 前面的轮次全部命中缓存 |
| 只发最新的用户消息 | ❌ 没有前缀可复用，全部未命中 |
| 重新排序对话历史 | ❌ 前缀变了 |

**💡 实操建议**：把整个 messages 数组原封不动地传，不要重新构建或截断（除非你明确想丢弃某些内容）。

---

### 3. 动态内容放最后（时间戳、用户 ID、随机种子统统往后挪）

```
❌ 错误示范（缓存命中率极低）：
[时间戳: 2026-08-24 14:32:01]
[用户ID: abc-123]
[系统提示词: 你是一个...]

✅ 正确示范（缓存命中率极高）：
[系统提示词: 你是一个...]
[对话历史...]
[时间戳: 2026-08-24 14:32:01]  ← 变的东西全放最后
[用户ID: abc-123]
[用户最新问题]
```

**💡 实操建议**：审查你的 prompt 模板，把所有**每次请求都会变的东西**挪到最末尾。

---

### 4. 使用平台提供的显式缓存控制（Claude 用户必看）

Anthropic Claude 支持**手动标记缓存断点**：

```python
# Claude API 示例
{
    "role": "user",
    "content": [
        {
            "type": "text",
            "text": "超长的系统提示词或文档...",
            "cache_control": {"type": "ephemeral"}  # 👈 标记这里为缓存断点
        },
        {
            "type": "text",
            "text": "用户的具体问题..."  # 这部分不缓存，每次变
        }
    ]
}
```

**效果**：你明确告诉 Claude "这段前面的值得存"，它就会强制缓存，而且缓存 TTL 比自动缓存更长（Claude 的自动缓存 5 分钟没活动就过期，显式标记的最长可以保留 **1 小时**）。

OpenAI 目前是**自动前缀缓存**，不需要手动标记，但你可以通过保持前缀一致来蹭到。

---

### 5. 长文档 / 知识库内容放用户输入的前部

如果你做 RAG（检索增强生成），把检索到的文档放在 prompt 靠前的位置：

```
[系统提示词]          ← 固定
[检索到的文档段落]     ← 虽然不同查询文档不同，但同一文档多次被查时能命中
[对话历史]            ← 追加式增长
[用户问题]            ← 每次变
```

**💡 实操建议**：如果用户反复问同一个文档相关的问题，这个文档部分会一直命中缓存。

---

### 6. 同一个会话尽量用同一个模型

```
claude-sonnet-4-20250514  → 缓存 ✅
claude-sonnet-4-20250514  → 缓存 ✅
claude-opus-4-20250514    → 缓存 ❌（模型变了，缓存不共享）
```

**💡 实操建议**：生产环境锁定模型版本号，别用别名（如 `claude-3-5-sonnet-latest`），因为别名背后可能悄悄换版本。

---

### 7. 避免"无意义的小改动"

这些操作会让缓存失效，但你可能根本没意识到：

| 操作 | 影响 |
|---|---|
| 在 prompt 开头加个 `\n`（换行） | ❌ 前缀变了，缓存废了 |
| JSON 格式里调换 key 的顺序 | ❌ 字符串变了 |
| 用不同的序列化方式（单引号变双引号） | ❌ 字符串变了 |
| 每次重新格式化 markdown | ❌ 可能多出空格 |

**💡 实操建议**：prompt 模板用**确定性渲染**（比如 Jinja2 模板，不要每次手动拼字符串），确保输出完全一致。

---

### 8. 批量请求时，让相似请求"扎堆"

如果你要处理 1000 条数据：

```
❌ 随机顺序处理：请求 A（文档1）→ 请求 B（文档2）→ 请求 A（文档1）
   → 文档1 的缓存可能已经过期了

✅ 按文档分组：文档1 的 50 条请求连续发 → 文档2 的 30 条请求连续发
   → 缓存一直在活跃状态，不会过期
```

**💡 实操建议**：如果处理批量任务，按共享前缀分组，连续发送。

---

### 9. 了解平台的缓存 TTL（过期时间）

| 平台 | 自动缓存 TTL | 显式缓存 TTL |
|---|---|---|
| **Claude (Anthropic)** | 5 分钟无活动 | 最长 1 小时 |
| **OpenAI** | 5~60 分钟（按负载动态） | 不支持显式控制 |
| **Gemini** | 约 1 分钟（默认） | 支持 `cached_content` API，最长数小时 |

**💡 实操建议**：如果用户的两次请求间隔可能超过 5 分钟，考虑用 Claude 的显式 `cache_control` 或 Gemini 的缓存 API 来延长有效期。

---

### 10. 监控缓存命中率（别猜，看数据）

大部分平台在 API 响应里会返回缓存信息：

```json
// Claude 响应示例
{
  "usage": {
    "input_tokens": 10000,
    "cache_creation_input_tokens": 0,      // 这次创建了多少新缓存
    "cache_read_input_tokens": 8500,        // 👈 这 8500 个 Token 命中了缓存（打折！）
    "output_tokens": 500
  }
}
```

```json
// OpenAI 响应示例
{
  "usage": {
    "prompt_tokens": 10000,
    "prompt_tokens_details": {
      "cached_tokens": 8500                 // 👈 命中缓存的 Token 数
    }
  }
}
```

**💡 实操建议**：在日志里打印这些字段，算一下 `cache_read / total_input` 的比例。如果低于 50%，说明你的前缀策略有问题。

| 优先级 | 动作 | 预期省多少钱 |
|---|---|---|
